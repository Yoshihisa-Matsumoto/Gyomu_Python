# gyomu-config：複数ファイル取得・MergePolicy 設計方針

## 1. 目的と前提

`gyomu-config` に複数の設定ファイルを取得し、指定された方針に従って最終的な設定値を決定する仕組みを追加する。

主なパッケージの責務は次のとおり。

- `gyomu-schema`：設定モデルなどのスキーマ定義
- `gyomu-infra`：JSON ファイルなどの低レベルな I/O
- `gyomu-config`：設定ファイルの取得・保存、キャッシュ、マージ方針の適用
- `gyomu-test`：モデルデフォルトなどのドメイン固有の優先順位と候補の決定

**重要：** 現時点では、`gyomu-test` でフィールド単位のマージを実装する必要はない。まずは複数ファイル取得と、優先順位の高い候補を採用する戦略を実装する。

## 2. 既存 API

既存の単一ファイル取得 API は変更しない。

```python
def retrieve_config[T: BaseModel, C](
    request: ConfigRequest[T, C],
) -> Result[T | None, ConfigError]:
    ...
```

パス解決用 Protocol：

```python
class ConfigPathResolver[C](Protocol):
    def get_path(
        self,
        context: C,
    ) -> Result[Path, ConfigError]:
        ...
```

`ConfigRequest[T, C]` は `config_type`、`context`、`path_resolver` を持つ。

単一ファイル取得の内部実装は、すでに `retrieve_single_config` に分離済み。

- ファイルが存在しない場合は `Success(None)`。
- 読み込み・JSON 解析・モデル検証に失敗した場合は `Failure(ConfigError)`。
- 既存の `retrieve_config` と `ConfigRequest` は維持する。

## 3. 複数ファイル取得 API

### 方針

- 単一ファイル取得 API とは別に追加する。
- 複数のパスは Request に直接固定せず、専用 Resolver から取得する。
- 既存の `ConfigPathResolver` は変更しない。
- 新たに `ConfigPathsResolver` を導入する。
- `MergePolicy` は複数ファイル取得 Request の属性として持たせる。
- 必要なデフォルト値も取得要求の候補として扱えるようにする。
- キャッシュは `gyomu-config` 内部で管理し、公開 API にキャッシュの利用方法を露出させない。

Resolver の暫定案：

```python
class ConfigPathsResolver[C](Protocol):
    def get_paths(
        self,
        context: C,
    ) -> Result[tuple[Path, ...], ConfigError]:
        ...
```

返すパスの順序と優先順位の対応関係は、具体的な API 設計時に明確にする。

## 4. MergePolicy と MergeStrategy

### MergePolicy の責務

`MergePolicy` は、設定取得時に適用するマージ方針を表し、`MergeStrategy` を保持する。

設定候補の順序やデフォルト候補など、マージ処理に必要な条件をどこまで `MergePolicy` が保持するかは、具体的なインターフェース設計時に決定する。

### MergeStrategy の責務

`MergeStrategy` は、与えられた設定候補から最終的な設定値を決定する処理を表す。

- 現時点では、優先順位の高い有効な候補を採用する戦略を実装する。
- 将来的には、複数の設定を統合する戦略も扱えるようにする。
- `gyomu-config` は標準戦略を提供する。
- 将来、Protocol を通じて独自の戦略に差し替えられるようにする。

具体的な Protocol、メソッド名、引数・戻り値の型は未確定。

### 設計上の原則

- `gyomu-config` はモデルの定義場所など、ドメイン固有の優先順位を解析しない。
- `gyomu-test` などの呼び出し側が、用途に応じた候補と優先順位を決める。
- 今すぐ汎用的なマージフレームワークを作らない。
- 将来の拡張を妨げない責務分担を維持する。

## 5. 将来のフィールド単位のマージ

将来的には、VS Code の設定のように、複数の設定モデルをフィールド単位で統合することを想定する。

例：

- 下位設定：`timeout=30, retries=3`
- 上位設定：`timeout=60`
- 統合結果：`timeout=60, retries=3`

ただし、単純な `BaseModel` 派生型すべてに適用できる画一的なルールを、現時点で定義することは難しい。

## 6. 未設定の扱い

永続化形式や、他のプログラムによる設定ファイルの編集を考慮し、マージ上は次の状態を未設定として扱う。

- 設定ファイルが存在しない。
- 設定項目が存在しない。
- 設定項目の値が `None`。

未設定の候補は採用せず、次の候補を確認する。

有効な設定値が見つかれば、それを採用する。すべて未設定の場合は、デフォルト候補などの最終的な扱いに従う。

**注意：** この方針では、明示的な `None` と未指定を区別しない。`None` 自体を有効な設定値として保存・適用する必要が生じた場合は、未設定と区別できる永続化上の表現を別途検討する。

ファイルが存在しないことと、ファイルの読み込み・検証に失敗したことは区別する。

- ファイルが存在しない：正常系として未設定を返す。
- ファイルの読み込み・検証に失敗：エラーを返す。通常の候補探索では、次の候補に黙ってフォールバックしない。

## 7. デフォルト値の扱い

デフォルト値は、必要に応じてマージ対象の候補に含める。

例：

1. ワークスペース設定
2. プロジェクト設定
3. 機能の標準デフォルト設定

すべての上位候補が未設定であれば、最後のデフォルト候補を採用する。

これにより、デフォルト値の適用もマージ方針の一部として扱える。

ただし、デフォルト候補の生成方法まで設定ファイルと統一する必要はない。Python のデフォルト値やヘルパー関数呼び出しなどは、呼び出し側が候補として用意することもできる。

## 8. 優先順位の決定は呼び出し側の責務

`gyomu-test` のモデルデフォルト設定では、用途によって優先順位が異なる。

### プリミティブ型など

1. ワークスペース共通設定
2. プロジェクト共通設定
3. Python のデフォルト値

### ヘルパー関数で生成するモデル型

1. ワークスペース共通設定
2. 生成対象モデルの型が定義されているパッケージの設定
3. 生成対象モデル自身が定義されているパッケージの設定
4. 引数なしのヘルパー関数呼び出し

同一スコープ内に共通設定とヘルパー関数の両方が存在する場合は、手書きの式を減らすため、既存のヘルパー関数を共通設定より優先する。

これらの優先順位は `gyomu-test` が決定する。`gyomu-config` はドメイン情報を解析せず、渡された候補と方針に従う。

## 9. エラーの責務

- `ConfigError`：`gyomu-config` におけるパス解決、ファイル読み込み、JSON 解析、モデル検証などの失敗。
- `TestingError`：`gyomu-test` におけるドメイン解析の失敗。
- ファイルが存在しない場合：エラーではなく未設定として扱う。

`gyomu-test` が必要なドメイン情報を先に解析し、その結果を Resolver に渡す。Resolver は設定ファイルのパス解決に専念する。
