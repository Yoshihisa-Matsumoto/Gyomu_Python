# Gyomu Test — Roadmap

## 1. Overview

`gyomu-test` は、Gyomu Python における Unit Test の設計・作成・検証・保守を支援するパッケージである。

単にテストコードを LLM で生成するのではなく、既存コードの解析結果、仕様、関数の Signature、テスト設計、既存のテストヘルパーなどを活用し、テストを体系的に管理できる仕組みを構築する。

本プロジェクトでは、次の2つの開発フローを対象とする。

### 1.1 Implementation-first

既存の実装を起点にテストを設計・作成する。

1. 実装コードを解析する。
2. 対象の構造・依存関係・型情報を取得する。
3. 仕様や実装を確認し、テスト対象と期待動作を整理する。
4. テストケースを設計する。
5. テストコードを生成する。
6. テストを実行し、結果を検証する。

初期実装では、このフローを中心に進める。

### 1.2 Test-first / TDD

実装が存在しない段階から、仕様や Signature を起点にテストを設計・作成する。

1. 実現したい機能の仕様・契約を定義する。
2. 関数の Signature やデータモデルを定義する。
3. 期待動作とテストケースを設計する。
4. テストコードを作成する。
5. テスト対象の実装を作成する。
6. テストを実行し、実装を検証・修正する。

このフローは将来の正式な対応範囲とする。初期段階ですべてを実装する必要はないが、テスト設計が既存実装の存在を必須とする構造にはしない。

### 1.3 Goals

- 既存のテストヘルパーを体系的に把握し、再利用を促進する。
- テスト対象とテストケースを整理し、テスト設計を管理する。
- AI Compiler を利用してテストコードの生成を支援する。
- 生成されたテストを実行し、必要に応じて修正を支援する。
- 既存コードと新規開発の両方で、テストの作成・保守を効率化する。
- Implementation-first と Test-first の両方を共通の基盤で扱えるようにする。

### 1.4 Non-goals

- Python のソースコード解析機能を独自に再実装すること。
- すべてのテスト設計を LLM の判断だけに委ねること。
- 初期段階で完全自動の TDD サイクルを実現すること。
- テストコードの生成と同時に、既存コードを無条件で書き換えること。
- 仕様が不明確な場合に、実装の現状だけを正しい仕様として扱うこと。

## 2. Package Responsibilities

### 2.1 gyomu-test

Unit Test の設計・作成・管理に関する、LLM に依存しないロジックを担当する。

主な責務：

- テストヘルパーの Inventory
- テスト対象の Inventory
- テスト設計とテストケースの管理
- テスト生成対象の決定
- テストコード生成のための入力情報の整理
- 生成結果の構造的な検証
- テスト実行結果の集約・分析
- 既存テストとテスト設計の整合性確認
- テスト関連の変更候補・修正候補の管理
- モデルのヘルパー関数生成に必要なデフォルト値の特定
- 型情報に基づくデフォルト値候補の生成
- デフォルト値設定の保存先候補の生成
- モデル定義パッケージ、型定義パッケージ、ワークスペースのスコープの判定
- 設定が不足している場合に必要なユーザー判断事項の整理

候補の生成とユーザーによる選択は区別する。`gyomu-test` は型情報やモデルの依存関係を基に候補を生成するが、候補の採用や保存先の最終決定は行わない。
テスト設計の共通モデルは、実装コードから取得した情報だけでなく、仕様や人が承認した設計情報からも構築できるようにする。

### 2.2 gyomu-ai-compiler

LLM を利用する処理と、その入出力を構築する処理を担当する。

主な責務：

- テスト設計支援のためのプロンプト・入力コンテキストの構築
- テストケース設計結果の構造化
- テストコード生成
- テスト失敗時の原因分析・修正案生成
- LLM の出力形式・スキーマの管理

テストの選択、Inventory の照合、既存ファイルの管理など、通常のプログラムで決定できる処理は `gyomu-test` 側で行う。

### 2.3 gyomu-python-analysis

Python のソースコード解析を担当する。

主な責務：

- モジュール、クラス、関数、変数などの解析
- 関数の Signature、型注釈、戻り値の型の取得
- クラスの継承関係、デコレーター、依存関係の取得
- Pydantic モデルや dataclass の判定に必要な情報の提供
- 既存の解析キャッシュの再利用

`gyomu-test` は既存の解析結果を利用する。必要な情報が不足している場合は `gyomu-python-analysis` の機能を拡張し、解析ロジックを `gyomu-test` に重複実装しない。

### 2.4 gyomu-infra

ファイルシステムやその他のインフラ処理を担当する。

主な責務：

- ファイルの読み書き
- テストファイルの列挙
- 必要に応じたプロセス実行などのインフラ操作
- ファイル変更に関する基盤処理

### 2.5 gyomu-schema

パッケージ間で共有するモデルを担当する。

テスト設計、テストケース、生成結果など、複数パッケージで共有するモデルは原則として `gyomu-schema` に配置する。

一方、`gyomu-test` 内だけで使用する一時的な状態や内部処理用のモデルは、無理に共通スキーマへ移動せず、`gyomu-test` 内に配置する。

### 2.6 gyomu-workflow / CLI

汎用 CLI は、個別機能が提示する変更候補をユーザーが確認・選択・編集・承認するための共通機能を提供する。

主な責務：

- 変更候補と選択肢の提示
- 候補の選択・編集
- 設定の保存先の選択
- 承認・拒否・キャンセルの管理
- 承認された変更要求の適用担当への引き渡し
- 適用結果と失敗状態の管理

候補の生成や、候補がどのような意味を持つかというドメイン固有の判断は、各機能パッケージが担当する。

## 3. Architecture Principles

### 3.1 Test Design must be independent of implementation

テスト設計は、現在の実装を解析した結果だけから作られるものではない。

テスト設計に利用する情報は、少なくとも次のように区別する。

| 情報の種類 | 内容 | 主な取得元 |
|---|---|---|
| Code Facts | 現在のコードに存在する構造・型・依存関係 | `gyomu-python-analysis` |
| Contract / Specification | 関数やクラスが満たすべき契約・仕様 | 仕様書、設計情報、人の入力 |
| Test Design | 期待動作、境界条件、異常系、テストケース | 仕様と設計判断 |
| Test Implementation | pytest などで実行可能なテストコード | テストコード生成・既存ファイル |

これらは関連付けるが、同一の情報として扱わない。

特に、**現在の実装で観測できる動作と、本来満たすべき期待動作は別の情報**である。実装にバグがある場合、実装の現状をそのまま正解としてテストに固定してはならない。

### 3.2 Test Design is the common foundation

Implementation-first と Test-first は、異なる情報から開始するが、最終的には共通のテスト設計を利用する。

- Implementation-first は、既存の Code Facts をテスト設計の入力に利用する。
- Test-first は、仕様、Signature、設計情報をテスト設計の入力に利用する。
- 両者とも、期待動作とテストケースを定義した後は、共通のテストコード生成・検証処理を利用する。

テスト設計のモデルに、実装解析結果しか保持できない構造を持ち込まない。

### 3.3 Planned definitions must be representable

Test-first では、実装コードや通常の解析キャッシュがまだ存在しない場合がある。

そのため、将来的には次のような情報を、実装コードがなくてもテスト設計に利用できるようにする。

- 関数・メソッドの Signature
- 引数と戻り値の型
- 期待される振る舞い
- 前提条件と事後条件
- エラー条件
- データモデルの構造
- テストケースと期待結果

これらの入力方法や保存形式は、必要になった段階で具体化する。初期段階では TDD 専用の大規模な仕組みを作らず、共通モデルが実装依存にならないことを優先する。

### 3.4 Deterministic logic first

プログラムで確定的に判断できることは、可能な限りプログラムで処理する。

LLM は、期待動作の整理、テストケースの提案、テストコードの生成、失敗原因の分析など、言語理解や推論が必要な処理に利用する。

LLM の提案を、そのまま承認済みの仕様や正しいテストとして扱わない。

### 3.5 Safe generation and modification

初期段階では Inventory とレポートを中心とし、既存コードを自動変更しない。

コード生成・修正を導入する段階でも、既存ファイルを無条件に上書きするのではなく、変更候補の提示、差分確認、検証を経て適用できる設計とする。

## 4. Development Workflows

### 4.1 Shared workflow model

両方の開発フローで共通となる概念を整理する。

1. **Target** — テスト対象の関数、メソッド、クラスなど
2. **Definition** — Signature、型、仕様、設計上の契約
3. **Test Design** — テスト対象の期待動作とテストケース
4. **Test Code** — 実行可能なテストコード
5. **Validation** — テストの実行と結果の確認

すべての対象に対して、すべての情報が最初から揃っている必要はない。

例えば、実装前の対象には Code Facts がなくてもよい。逆に、既存コードがある場合でも、仕様や期待動作が不明確なことがある。

不足情報を明示し、必要に応じて人の確認を求める。

### 4.2 Implementation-first workflow

初期実装で優先するフロー。

1. 既存のソースコードと解析キャッシュを取得する。
2. テスト対象と既存テストを Inventory 化する。
3. 必要な仕様・期待動作を確認する。
4. テスト設計を作成する。
5. テストコードを生成する。
6. テストを実行して検証する。
7. 不足や失敗をレポートする。

最初は既存コードを対象にすることで、実装済みの解析・キャッシュ基盤を活用できる。

### 4.3 Test-first / TDD workflow

将来的に追加するフロー。

1. 仕様や要求からテスト対象の Definition を用意する。
2. Signature、型、期待動作を定義する。
3. テスト設計を作成する。
4. テストコードを生成する。
5. テストコードを実行可能な状態にする。
6. 対象の実装を作成する。
7. テストを実行して、実装が契約を満たすか検証する。
8. 必要に応じて実装または承認済みのテスト設計を修正する。

テストが失敗した場合は、単にテストを通すために期待結果を変更するのではなく、失敗原因を確認する。仕様変更が必要なら、期待動作の変更を明示的に承認する。

### 4.4 Initial scope versus future scope

| 項目 | 初期段階 | 将来 |
|---|---|---|
| 既存実装の解析 | 対応 | 継続 |
| 既存ヘルパーの Inventory | 優先実装 | 継続 |
| 既存実装からのテスト設計 | 対応 | 継続・改善 |
| 共通のテスト設計モデル | 実装非依存を意識して設計 | 拡張 |
| 実装前の Signature / Contract | 専用ワークフローは未実装 | 対応 |
| テスト先行のコード生成 | 未実装 | 対応 |
| テスト実行と結果分析 | 段階的に実装 | 拡張 |
| 実装とテストの反復的な修正 | 初期対象外 | 対応 |

## 5. Phase 1 — Helper Inventory

### 5.1 Objective

既存の `test_support` に存在するヘルパーを解析し、既存の dataclass / Pydantic モデルなどに対応するファクトリー関数を体系的に把握する。

この Phase ではコードの自動変更を行わず、現状と不足をレポートする。

### 5.2 Current conventions

各パッケージのテスト支援コードは、原則として `test_support/` に配置する。

基本構成：

- `__init__.py`
- `helpers.py`
- 必要に応じた追加のヘルパーモジュール
- `fixtures/` — テストで使用する入力データやプロジェクト構造

ヘルパーの多くは、モデルを生成するファクトリー関数である。

例えば、`PydanticAiModelDefinition` に対して `create_pydantic_ai_model_definition` のような命名を用いる。

原則として、通常のファクトリー関数は引数なしでも呼び出せるようにし、フィールドに妥当なデフォルト値を設定する。ネストされたモデルを必要とする場合も、対応するファクトリーを再利用して生成できることが望ましい。

一方、テスト用の登録処理や実 LLM 接続など、モデル生成以外のヘルパーも存在する。これらを一律にモデルファクトリーとして扱わない。

### 5.3 Inventory targets

#### Model inventory

`gyomu-python-analysis` の解析結果を利用し、次の対象を抽出する。

- dataclass
- Pydantic `BaseModel` の派生クラス
- 必要に応じて、モデルファクトリーの対象となるその他の型

Pydantic モデルの判定では直接の `BaseModel` 継承だけでなく、間接的な継承関係も考慮する。

継承元や import の解決が不完全な場合は、誤って確定判定せず、未解決として記録する。

#### Helper inventory

各パッケージの `test_support` から、次の情報を取得する。

- ヘルパー関数名
- 定義ファイル
- 引数とデフォルト値
- 戻り値の型
- 関数の役割
- 関連するモデル
- モジュール間の依存関係

ソースコード解析機能が不足する場合は `gyomu-python-analysis` を拡張する。

#### Candidate matching

モデルとヘルパーの対応関係を調べる。

- モデルに対応するヘルパーが存在しない
- 同一モデルに対するヘルパーが複数存在する
- 同じ名前のヘルパーが異なる型を返す
- 命名規則と戻り値の型が一致しない
- 戻り値の型が不明である
- モデルファクトリーではないヘルパーが存在する
- ヘルパーの依存先が不足している可能性がある

名前だけで対応関係を確定せず、戻り値の型や実際の定義も考慮する。

### 5.4 Module organization

ヘルパーを `helpers.py` に集約するか、別モジュールに分割するかを評価する。

ファイルの行数だけで機械的に分割せず、次の観点を利用する。

- 役割の違い
- 対象モデルのまとまり
- ヘルパー同士の依存関係
- import の複雑さ
- テストからの利用方法
- 既存プロジェクトの慣習

既存の `concept_helpers.py` なども、単に名前を統一するのではなく、実際の責務を調べて判断する。

テスト用の入力データを置く `fixtures/` と、オブジェクト生成ロジックを持つヘルパーモジュールは区別する。

### 5.5 Planned location

`gyomu-test` 内の責務は、次の位置から開始する。

`gyomu_test/helper/inventory/`

内部構成は、Inventory の責務と実装規模が明確になった段階で決める。初期段階から細かい抽象化や多数のモジュールを設けない。

### 5.6 Deliverables

- モデル Inventory
- ヘルパー Inventory
- モデルとヘルパーの対応関係
- 不足・重複・不一致のレポート
- 分割候補のレポート
- 未解決事項の一覧

### 5.7 Completion criteria

- 対象パッケージのモデルを解析できる。
- 対象パッケージの `test_support` を解析できる。
- モデルとヘルパーの対応関係を確認できる。
- 不足・重複・不一致を識別できる。
- 解析不能な項目を黙って除外せず、レポートできる。
- Inventory 実行によって既存ファイルが変更されない。

## 6. Phase 2 — Helper Standards and Generation

### 6.1 Objective

Phase 1 で把握した現状を基に、ヘルパーの標準と生成機能を整備する。

### 6.2 Standards

- モデルファクトリーの命名規則を統一する。
- 可能な範囲で引数なしで呼び出せるようにする。
- デフォルト値を明示する。
- ネストされたモデルには既存ファクトリーを再利用する。
- 既存のヘルパーとの互換性を考慮する。
- モデルファクトリーと一般的なテスト支援関数を区別する。

### 6.3 Generation

- 不足しているヘルパーの生成候補を作成する。
- 既存ヘルパーの修正候補を作成する。
- 変更差分を提示する。
- 生成結果を型検査・Lint・テストで検証する。

初期段階では、既存ファイルの無条件な上書きを避ける。

### 6.4 Future extension

将来的には、まだ実装されていないデータモデルの設計情報からも、必要なファクトリーやテスト支援コードを設計できる余地を残す。

ただし、Phase 2 では既存コードからの生成を優先する。


### 6.5 Default Configuration

ヘルパー関数の生成では、対象モデルの各フィールドに妥当なデフォルト値を設定できる必要がある。

デフォルト値の決定に必要な設定が存在しない場合は、次の手順で対応する。

1. `gyomu-test` が対象モデルと各フィールドの型情報を解析する。
2. 型情報と依存関係を基に、必要なデフォルト値と候補を生成する。
3. 設定が存在しない場合は、設定を新規作成するための候補を生成する。
4. 保存先候補を、ワークスペース、モデル定義パッケージ、型定義パッケージなどのスコープから生成する。
5. 汎用 CLI が候補をユーザーに提示し、値と保存先を選択・編集してもらう。
6. 承認された内容を設定として保存する。
7. 保存された設定を利用してヘルパー関数を生成する。

例えば、次のモデルでは、各フィールドに対応する型の設定値が必要になる。

- `package: str` — `str` のデフォルト値
- `completed_steps: tuple[PipelineStep, ...]` — `PipelineStep` のデフォルト値を利用したタプル
- `fingerprints: Fingerprints` — `Fingerprints` のデフォルト値

このとき、コンテナ型の設定と、その要素型の設定を区別する。型の構造に基づいて必要な設定を特定し、設定値の候補を生成する。

保存先候補の生成は `gyomu-test` の責務であり、最終的な保存先の選択は汎用 CLI の責務とする。

## 7. Phase 3 — Test Target Inventory and Design

### 7.1 Objective

テスト対象を整理し、対象ごとに必要なテストケースを管理できるようにする。

### 7.2 Test target inventory

- 関数・メソッド・クラスの列挙
- 既存のテストコードとの対応付け
- 対象の引数・戻り値・型情報の整理
- 依存関係と関連するモデルの整理
- テストが存在しない対象の抽出
- テスト対象の状態と未解決事項の管理

### 7.3 Test design

テストケースの設計では、少なくとも次の観点を考慮する。

- 正常系
- 境界値
- 異常系
- 入力バリデーション
- 依存先との相互作用
- 戻り値や副作用
- 非同期処理
- エラーの伝播
- 必要に応じた状態遷移

すべての対象に同じ観点を機械的に適用するのではなく、対象の契約や性質に応じて選択する。

### 7.4 Contract and test design sources

テスト設計の入力元は、既存の実装解析だけに限定しない。

- 既存ソースコードの解析結果
- 既存のテストコード
- 仕様書や人が作成した設計情報
- Signature と型情報
- 人が承認した期待動作
- 既存テストの実行結果

将来、Test-first を実装するときは、実装前の Signature や仕様から同じテスト設計を構築できるようにする。

### 7.5 Human review

仕様から一意に判断できない期待動作は、LLM が推測した結果を確定仕様として扱わない。

不明点を提示し、人の判断を得た上でテスト設計に反映する。

### 7.6 Deliverables

- テスト対象 Inventory
- テストケースの設計情報
- 対象とテストケースの対応関係
- 期待動作の根拠
- 未解決の仕様・設計事項

---

## 8. Phase 4 — Test Code Generation

### 8.1 Objective

承認されたテスト設計から、pytest で実行できるテストコードを生成する。

### 8.2 Responsibilities

`gyomu-test` は、対象・テストケース・必要なヘルパー・生成対象を整理する。

`gyomu-ai-compiler` は、必要な入力コンテキストを構築し、テストコードの生成を行う。

### 8.3 Generation principles

- 既存のテストスタイルを可能な限り尊重する。
- 既存ヘルパーを再利用する。
- 仕様と期待結果が明確なテストを優先する。
- 1つのテストが検証する内容を明確にする。
- 必要に応じて pytest の parametrization を利用する。
- テスト対象の実装を推測して書き換えない。
- テスト設計にない期待動作を勝手に追加しない。

### 8.4 Workflow independence

生成処理は、テスト対象の実装が存在することを必須条件にしない。

Implementation-first では既存の解析結果を利用し、Test-first では仕様・Signature・承認済みのテスト設計を利用する。

生成時に必要な情報が不足している場合は、不足を明示する。

### 8.5 Validation before adoption

生成したテストコードは、適用前に少なくとも構文・型・Lint・テスト実行などの適切な検証を行えるようにする。

実装前の TDD では、対象の実装がまだ存在しないため、検証時点で未実装による失敗と、テストコード自体の不備を区別する必要がある。

---

## 9. Phase 5 — Validation and Repair

### 9.1 Objective

テストを実行し、その結果を分析して必要な対応を支援する。

### 9.2 Validation

- テスト実行結果の取得
- 失敗したテストの特定
- 例外と失敗メッセージの整理
- テスト対象との関連付け
- 既知の失敗と新規の失敗の識別
- 修正が必要な箇所の候補提示

### 9.3 Failure classification

失敗を一律に「テストコードの問題」と判断しない。

少なくとも、次の可能性を区別する。

- 実装の不具合
- テストコードの不具合
- テスト設計と仕様の不一致
- テスト環境・依存関係の問題
- 外部サービスや非決定的な要因
- 現時点では原因を確定できない失敗

### 9.4 Repair

修正候補は、原因分析と既存の契約を踏まえて提示する。

テストを通すためだけに期待結果を変更したり、実装の不具合を隠すようにテストを弱めたりしない。

仕様変更が必要な場合は、テスト設計の更新として明示的に扱う。

### 9.5 TDD extension

Test-first では、テストが失敗すること自体が初期段階では正常である。

そのため、将来的には次の状態を区別する。

- テストコードが未検証
- テストが実装未完成のため失敗
- 実装の不具合により失敗
- テストコードの不具合により失敗
- テスト成功

初期段階で状態管理のすべてを実装する必要はないが、失敗を一律に異常とみなす設計は避ける。

---

## 10. Phase 6 — Workflow and CLI Integration

### 10.1 Objective

個別機能を `gyomu-workflow` と CLI から利用できるようにする。

### 10.2 Integration candidates

- Helper Inventory の実行
- テスト対象 Inventory の実行
- テスト設計の作成・確認
- テストコード生成
- テスト実行と結果確認
- 必要に応じた修正候補の作成

### 10.3 Workflow modes

将来的には、少なくとも次のような起動方法を扱えるようにする。

- 既存コードからテストを作成する。
- 仕様・Signature から先にテストを作成する。
- 既存テストを検証・保守する。

ただし、初期段階ではすべての操作を統合した大規模なワークフローを作らず、個別機能の完成と検証を優先する。


### 6.5 Default Configuration

ヘルパー関数の生成では、対象モデルの各フィールドに妥当なデフォルト値を設定できる必要がある。

デフォルト値の決定に必要な設定が存在しない場合は、次の手順で対応する。

1. `gyomu-test` が対象モデルと各フィールドの型情報を解析する。
2. 型情報と依存関係を基に、必要なデフォルト値と候補を生成する。
3. 設定が存在しない場合は、設定を新規作成するための候補を生成する。
4. 保存先候補を、ワークスペース、モデル定義パッケージ、型定義パッケージなどのスコープから生成する。
5. 汎用 CLI が候補をユーザーに提示し、値と保存先を選択・編集してもらう。
6. 承認された内容を設定として保存する。
7. 保存された設定を利用してヘルパー関数を生成する。

例えば、次のモデルでは、各フィールドに対応する型の設定値が必要になる。

- `package: str` — `str` のデフォルト値
- `completed_steps: tuple[PipelineStep, ...]` — `PipelineStep` のデフォルト値を利用したタプル
- `fingerprints: Fingerprints` — `Fingerprints` のデフォルト値

このとき、コンテナ型の設定と、その要素型の設定を区別する。型の構造に基づいて必要な設定を特定し、設定値の候補を生成する。

保存先候補の生成は `gyomu-test` の責務であり、最終的な保存先の選択は汎用 CLI の責務とする。

---

## 11. Persistent Knowledge and Cache

### 11.1 Principles

解析結果、設計情報、実行結果を同一の情報として扱わない。

- **Analysis Cache:** ソースコードから取得した解析結果
- **Inventory:** 対象やヘルパーの一覧と照合結果
- **Test Design:** 期待動作とテストケース
- **Test Code:** 実行可能なテストファイル
- **Validation Results:** テスト実行や検証の結果

既存の解析キャッシュを活用し、同じ解析を不必要に繰り返さない。

### 11.2 Source of truth

コード解析結果は、解析時点のコードの事実を表す。

一方、仕様や人が承認した期待動作は、コード解析結果とは別に保持する。

実装が変更されたときに、承認済みのテスト設計を無条件に上書きしない。

### 11.3 Implementation-first and Test-first compatibility

将来の TDD 対応では、実装前の Definition や Test Design を保持できる必要がある。

したがって、テスト設計の保存形式を、既存の解析キャッシュにしか存在しない情報へ直接依存させない。

保存先や更新戦略の詳細は、実際の利用要件に合わせて段階的に決定する。


### 11.4 Configuration Storage and Cache Consistency

設定ファイルの読み書きとキャッシュ管理は `gyomu-config` が担当する。

`gyomu-config` は、どの設定が必要か、どの値を候補とするか、どの保存先を採用するかを判断しない。呼び出し元から確定したリクエストに基づいて、設定の読み書きと検証を行う。

キャッシュはインスタンス内で管理し、ファイルの状態を基に有効性を判断する。

現在の実装では、設定ファイルの保存時にキャッシュを即時更新するのではなく、次回の取得時に実ファイルの状態とキャッシュに記録された状態を比較する。状態が異なる場合は古いキャッシュを破棄し、設定を再読み込みしてキャッシュを更新する。

この方式は、次回利用時に変更を検知する遅延検証型のキャッシュ管理である。ファイル状態の取得に失敗した場合はエラーを伝播し、古いキャッシュを有効な設定として返さない。

### 11.5 Configuration Scope and Merge Policy

設定の保存先スコープと、複数ファイルを読み込む際の優先順位は別の概念として扱う。

保存先候補は `gyomu-test` が生成し、汎用 CLI がユーザーの選択を受け付ける。一方、複数ファイルの読み込み順序と設定値の統合方法は `gyomu-config` のリクエストと `MergePolicy` によって決定する。

スコープ間の優先順位は設定の利用要件に応じて定義し、保存先の選択だけから暗黙に決定しない。

## 12. Implementation Order

以下の順序で進める。

### Phase 1: Helper Inventory

1. `gyomu-python-analysis` の既存解析情報を確認する。
2. モデルとヘルパーの抽出に必要な情報を整理する。
3. `test_support` の解析方法を確立する。
4. モデルとヘルパーの対応関係を照合する。
5. 不足・重複・不一致をレポートする。
6. 実際の複数パッケージで検証する。

### Phase 2: Helper Standards and Generation

1. Inventory の結果を確認する。
2. 命名・デフォルト値・ネストしたモデルの生成方針を定める。
3. 不足ヘルパーの生成候補を作成する。
4. 修正差分を提示する。
5. 型検査・Lint・テストで検証する。

### Phase 3: Test Target Inventory and Design

1. 既存のテスト対象とテストコードを整理する。
2. テスト対象とテストケースの対応を管理する。
3. 期待動作と仕様の根拠を扱えるようにする。
4. Implementation-first でテスト設計を検証する。
5. 実装がなくてもテスト設計を保持できることを確認する。

### Phase 4: Test Code Generation

1. テスト設計から必要な入力コンテキストを構築する。
2. `gyomu-ai-compiler` を通じてテストコードを生成する。
3. 既存のテストコードとの整合性を確認する。
4. 生成コードを検証する。

### Phase 5: Validation and Repair

1. テストを実行する。
2. 結果を収集・分類する。
3. 失敗原因の分析を支援する。
4. 修正候補を提示する。
5. 修正後の検証を行う。

### Phase 6: Workflow and CLI

1. 個別機能を `gyomu-workflow` へ統合する。
2. CLI から実行できるようにする。
3. 必要に応じて処理状態の永続化を追加する。
4. Test-first / TDD のワークフローを追加する。

この順序は初期実装の優先順位であり、共通モデルやインターフェースの設計において Test-first を排除することを意味しない。

## 13. Immediate Next Steps

まず Phase 1 の Helper Inventory から着手する。

### Step 1 — Existing analysis capabilities

- dataclass の識別方法を確認する。
- Pydantic モデルの直接・間接継承を判定する方法を確認する。
- 関数の引数・戻り値・デフォルト値を取得できることを確認する。
- `test_support` 配下のソースコードを解析対象にできるか確認する。
- 既存キャッシュから必要な情報を取得できるか確認する。

不足する情報があれば、`gyomu-test` に解析処理を重複実装せず、`gyomu-python-analysis` の拡張を検討する。

### Step 2 — Inventory design

まず、次の情報を照合できるモデルを設計する。

- 対象モデル
- 既存ヘルパー
- モデルとヘルパーの対応関係
- 不足・重複・不一致
- 解析不能・未解決の項目

初期段階では、ファイルの生成や修正は行わない。

### Step 3 — Real package verification

複数パッケージを対象に実際の `test_support` を解析し、命名規則の例外や、モデルファクトリー以外のヘルパーも適切に扱えることを確認する。

### Step 4 — Future workflow compatibility

Phase 1 では既存モデルと既存ヘルパーを対象にする。ただし、Inventory や Test Design の内部モデルを、必ず実装コードから取得しなければ作れない構造にしない。

この段階では TDD の入力形式やワークフローを実装しない。将来、仕様や Signature からテストを先に作れることを妨げない点を確認する。

## 14. Design Principles Summary

- **既存資産を再利用する:** ソース解析は `gyomu-python-analysis`、LLM 関連処理は `gyomu-ai-compiler` を利用する。
- **役割を分離する:** Inventory、照合、テスト設計管理は `gyomu-test`、インフラ処理は `gyomu-infra` が担当する。
- **テスト設計を実装から独立させる:** 実装の事実と、仕様・期待動作を区別する。
- **2つの開発フローを支える:** Implementation-first を先に実装し、Test-first / TDD は共通基盤の上に追加する。
- **初期段階で過剰設計しない:** まず Helper Inventory を完成させ、実際の解析結果と課題を確認する。
- **変更は慎重に適用する:** 最初はレポートを中心とし、コード生成・修正は検証可能な形で導入する。
- **不明な情報を推測で確定しない:** 未解決事項を明示し、人の判断が必要な箇所を区別する。
